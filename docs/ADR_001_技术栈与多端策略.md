# ADR 001：技术栈与多端策略

状态：建议，待确认 · 2026-11-10

## 背景

第一版发布手机端（iOS、Android），后续要扩展到电脑端等。应用含有高度敏感的密钥保管功能，同时需要调用各平台的硬件安全能力。

## 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. Flutter | 一套代码覆盖 iOS、Android、macOS、Windows、Linux；界面自绘，各端一致；Dart 可写纯逻辑包并复用于命令行工具 | 加密钱包领域的 Dart 库生态不如 JavaScript 丰富；需自写少量原生插件 |
| B. React Native（加 Expo） | 加密领域 JavaScript 库最丰富（viem、ethers、CCXT） | 桌面端支持较弱且分散；npm 依赖树庞大，供应链风险更高，对保险库不利 |
| C. 各端原生（Swift、Kotlin） | 平台安全能力最直接 | 每个平台重写一遍，个人项目不可承受 |
| D. Kotlin Multiplatform | 逻辑共享、界面可原生 | 桌面与 iOS 的界面方案成熟度不一；学习成本高 |

## 决定（建议）

选 A：Flutter。

配套的多端策略：

1. 业务逻辑全部放在纯 Dart 包中，不依赖 Flutter 界面库。
2. 平台差异全部收敛到 `ow_platform`，以接口加能力声明的方式提供，界面按能力降级。
3. 界面从第一天起就写在响应式外壳内，按宽度断点切换布局。
4. 第一版只构建和验收 iOS 与 Android；桌面端工程在需要时添加。

## 后果

- 交易所接口需用 Dart 自行实现签名与解析（四家，工作量可控）。
- 地址派生库需在 M0 专门评估。
- 硬件密钥需要自写 Swift 与 Kotlin 的最小插件。
- 不选网页端：浏览器环境无法提供同等的密钥保护，保险库不适合放在网页中。如将来需要网页，只做不含保险库的只读看板。
