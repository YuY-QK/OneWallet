# OneWallet 执行手册

> 写给接手开发的执行者（人或 AI）。目的只有一个：**按文档做，不跑偏**。
> 与其他文档冲突时的优先级见第 3 节。

## 1. 你在做什么

OneWallet 是本地优先的个人加密资产看板加离线密钥保险库。它**只看不动**：不签名、不转账、不交易。产品范围、页面、规则、架构、安全方案都已定稿，你的工作是按任务清单把它实现出来，而不是重新设计。

## 2. 开工前必读（按顺序）

1. `AGENTS.md`：协作规则与命令。
2. `docs/progress.md`：现在做到哪了。
3. `docs/TASKS.md`：任务清单，找到你要做的任务。
4. `docs/DEV_GUIDELINES_v1.0.md`：**第 1 节安全红线逐条读完**，其余通读。
5. `docs/IMPLEMENTATION_SPEC_v1.0.md`：类型名、接口、路由、表结构的约定。
6. 任务里"依据"指向的章节（PRD 的页面与规则、TECH_DESIGN、SECURITY_DESIGN 等）。

涉及保险库、应用锁、备份文件的任务，另须通读 `docs/SECURITY_DESIGN_v1.0.md` 全文。

## 3. 文档的权威顺序

发现文档之间矛盾时，按下列顺序取舍，并在交付说明中指出矛盾，同时修正排在后面的那份：

1. `DEV_GUIDELINES` 第 1 节安全红线
2. `SECURITY_DESIGN`
3. `PRD`（做什么）
4. `IMPLEMENTATION_SPEC`（叫什么、长什么样）
5. `TECH_DESIGN`、各 `ADR`
6. `UI_DESIGN_SYSTEM`、`PROTOTYPE`、`prototype.html`
7. `TASKS`、`DEVELOPMENT_PLAN`

代码与文档不一致时，以文档为准改代码；如果你认为文档错了，按第 7 节处理，不要悄悄让代码偏离。

## 4. 每个任务的工作流程

1. **领任务**：在 `docs/TASKS.md` 中按顺序取第一个未开始、依赖已满足、你的环境能做的任务（或用户指定的任务）。把状态改为 `[~]`。
2. **建分支**：从仓库默认分支的最新提交建 `feat/<任务编号>-<简述>`，如 `feat/M1-02-address-checksum`。用户另有指定时听用户的。
3. **读依据**：把任务"依据"里的章节读完。读完后如果对"做什么、做到什么程度"仍有疑问，按第 7 节处理。
4. **先写测试，再写实现**：验收条目能写成自动化测试的，都写成测试。
5. **自查**：运行 `tools/check.sh`，必须全部通过。对照 `DEV_GUIDELINES` 第 12 节的自查表。
6. **同步文档**：实现中确定下来的事实（选了哪个库、接口的实际路径、参数取值）写回对应文档；任务状态改为 `[x]` 加日期；完成一个里程碑时更新 `docs/progress.md`。
7. **提交**：按 `DEV_GUIDELINES` 第 8 节的格式，一个任务一个或几个提交，提交说明里带任务编号。
8. **交付说明**：按第 8 节的格式汇报。

一次只做一个任务。做完一个再领下一个。

## 5. 完成的定义

一个任务只有同时满足以下各条才算完成：

- 任务条目里的"验收"逐条满足；
- `tools/check.sh` 全部通过；
- 新增的业务逻辑有测试，覆盖率不低于 TECH_DESIGN 第 8 节的门槛；
- 没有触碰任何安全红线；
- 页面的空、加载、错误状态都已实现（PRD 第 8 节该页的"页面状态"）；
- 文案在 ARB 中；
- 文档已同步，`TASKS.md` 状态已更新。

带〔设备〕〔真机〕〔用户〕标签而你无法验收的部分：代码和自动化测试照常完成，状态标 `[!]`，写清楚还差哪一步验收、怎么验收。**不得把未验证的东西报告为已验证。**

## 6. 不要做的事

**范围**
- 不做 PRD 第 5 节"明确不包含"和"后续候选"里的任何东西，即使看起来顺手。
- 不添加任务没有要求的功能、设置项、页面、动画。
- 不为"将来可能需要"提前抽象；只实现当前任务需要的。

**架构**
- 不改变包的划分和依赖方向；不让 `check_deps.dart` 的规则变松（确需调整时按第 7 节）。
- 不替换已选定的技术：Flutter、Riverpod、go_router、Drift 加 SQLCipher、libsodium、`blockchain_utils`。
- 不改 IMPLEMENTATION_SPEC 中约定的名字、路由、表结构，除非先改文档并说明原因。
- 不引入统计、崩溃上报、广告、远程配置类的 SDK。

**安全**
- 不写任何签名、转账、下单、划转、提现的代码。
- 不自己实现或拼装密码学算法。
- 不让密钥类数据进入日志、异常、路由参数、状态对象、剪贴板、测试快照。
- 不在测试、样本、提交记录中使用真实的助记词、私钥、API Key。测试助记词只用 BIP39 公开测试向量。
- 不要求用户把助记词或 API Secret 发给你。需要真实凭据的验证由用户在自己的设备上完成。
- 不为了让检查通过而删除或跳过测试、放宽静态检查规则、加忽略注释。

**流程**
- 不直接向默认分支提交；不强制推送别人的分支。
- 不在一个任务里顺手改无关的代码。发现别处的问题，记在交付说明的"发现的问题"里。

## 7. 需要停下来问用户的情况

遇到下列情况，**停下来**，说明情况并给出你的建议，等用户答复后再继续（可以先做不受影响的其他任务）：

- 文档没有规定，而不同做法会影响用户可见的行为或数据格式。
- 你认为文档有错，或两份文档矛盾且权威顺序解决不了。
- 需要新增 `ow_vault` 的依赖，或需要放宽 `check_deps.dart` 的任何规则。
- 需要改动保险库文件格式、备份文件格式、密钥层级、算法或参数。
- 需要偏离 IMPLEMENTATION_SPEC 的约定。
- 选定的库无法满足需求，需要更换。
- 任务的实际工作量远超预期（比如需要先重构别的模块）。
- 需要用户提供东西：API Key、真机操作、余额核对、测试钱包、应用标识。

以下情况**不用问**，自己决定并在交付说明中写明：私有实现细节；组件内部结构；测试的组织方式；不影响行为的命名；第三方库的小版本；录制样本的具体内容。

## 8. 交付说明的格式

每完成（或受阻于）一个任务，用下面的结构汇报：

```
任务：<编号> <标题>
状态：完成 / 受阻（原因）
分支：<分支名>，提交 <短哈希>

做了什么：
- …

验收：
- <验收条目 1>：通过（对应测试：<文件或用例名>）
- <验收条目 2>：未验证——需要〔真机〕，步骤：…

检查：tools/check.sh 通过 / 失败（附输出）

文档改动：
- …

自行决定的事项：
- …

发现的问题（不在本任务范围内）：
- …

需要用户：
- …
```

## 9. 环境

- Flutter 3.47.9（Dart 3.13）。版本不同先切换到这个版本，不要顺手升级。
- 首次进入仓库：`flutter pub get`，然后 `tools/check.sh` 确认基线是绿的。基线不绿时先报告，不要在红的基线上开工。
- 没有设备的环境可以完成全部〔离线〕任务。
- 需要联网查官方文档时，把查到的结论和链接写进 `docs/EXTERNAL_APIS.md` 或对应 ADR，不要只留在对话里。

## 10. 已定事项速查

这些都已决定，不需要再讨论：

| 事项 | 决定 |
|---|---|
| 平台 | 第一版 iOS 与 Android；架构支持日后扩展桌面端 |
| 后端 | 没有。app 直连第三方数据服务与交易所 |
| 资金操作 | 一律不做 |
| 链 | Ethereum、BNB Chain、Arbitrum、Optimism、Base、Polygon、Bitcoin、Solana、Tron |
| 交易所 | Binance、OKX、Bybit、Bitget，只读 |
| 第一版不含 | 交易流水、盈亏、DeFi 仓位、NFT、推送、后台同步、云同步、会员 |
| 在 app 内生成新助记词 | 不做 |
| 助记词与私钥的复制按钮 | 不提供 |
| PIN | 6 位数字 |
| 计价货币 | USD（默认）、CNY |
| 加密备份 | 不含余额缓存和历史快照；默认不含交易所 API Key |
| 视觉 | 方向 A「沉稳金融」，见 UI_DESIGN_SYSTEM |
| 语言 | 界面简体中文；代码标识符英文；注释与文档中文 |
