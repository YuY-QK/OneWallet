# ADR 003：保险库加密方案

状态：已确认 · 2026-11-10

## 背景

保险库要同时满足三个相互牵制的要求：

1. 日常查看方便（生物识别即可）。
2. 设备丢失、文件被拷走时安全。
3. 换机或设备损坏后可以恢复。

硬件密钥满足 1 和 2，但绑定设备，无法满足 3。主密码满足 2 和 3，但每次输入不方便。

## 选项

| 选项 | 说明 | 问题 |
|---|---|---|
| A. 只用硬件密钥 | 密钥全部交给系统安全芯片 | 设备坏了就全丢，违背产品初衷 |
| B. 只用主密码 | 每次查看都输入主密码 | 不方便，用户会倾向于设短密码 |
| C. 双重包裹 | 随机主密钥被硬件密钥和主密码各包裹一次，任一可解 | 实现稍复杂 |
| D. 直接使用现成的密码管理器存助记词 | 不自己做 | 无法与备份清单、派生地址打通；这是用户明确想要的功能 |

## 决定

选 C，细节见 SECURITY_DESIGN 第 3 至 6 节。要点：

- 随机生成保险库主密钥；用 Argon2id 加 XChaCha20-Poly1305 做密码包裹；用平台硬件密钥做第二份包裹。
- 密码学实现使用 libsodium，只调用高层接口。
- 硬件包裹由自写的最小原生插件完成，只使用系统自带的安全框架，不引入第三方原生库。理由：这是最敏感的代码路径，自写约数百行、可逐行审阅，比引入一个功能庞杂的通用插件更可控。M0 验证时若发现现成插件质量足够且代码量小，可改用并记录。
- 另设独立的加密备份文件格式，只依赖备份密码，格式公开，并提供独立解密工具。
- 保险库作为独立的包，禁止任何网络依赖，由 CI 强制。

## 后果

- 主密码遗忘且生物识别失效时，数据不可恢复。这一点必须在界面上反复明示。
- 需要维护两个平台的原生代码，并做真机专项验证。
- 备份文件格式一经发布就必须长期向后兼容。
- 对外发布之前必须经过第三方安全审计。
